# Boc body is not atomic across inner calls

`YZC-0124`

**A boc that calls another boc stops holding its resources (cowns) at that call, and the rest of
its body runs with nothing held.** Two calls that share a resource can overlap, and the field
writes after the call are unprotected.

## Observed

Found while writing a demo for [`Concurrency.md`](../../Features/Concurrency.md): a ping-pong
match holds two players and a table for one second. Two matches on the same table should run one
after the other.

```yz
Player: { name String; played Int }
Table:  { name String; games Int }

Match: {
    a Player
    b Player
    t Table
    play: {
        print("start ${a.name} v ${b.name} on ${t.name}")
        time.sleep(1)
        a.played = a.played + 1
        b.played = b.played + 1
        t.games = t.games + 1
        print("done  ${a.name} v ${b.name}")
    }
}

main: {
    alice: Player("alice", 0)
    bob:   Player("bob", 0)
    carol: Player("carol", 0)
    dave:  Player("dave", 0)
    t1: Table("t1", 0)
    t2: Table("t2", 0)

    print("open:  ${time.now()}")
    Match(alice, bob,  t1).play()
    Match(carol, dave, t1).play()
    print("close: ${time.now()}")
    print("games: alice ${alice.played}, bob ${bob.played}, carol ${carol.played}, dave ${dave.played}")
    print("tables: t1 ${t1.games}, t2 ${t2.games}")
}
main()
```

Output with `yzc v0.5.0-e08b58a`. Both matches start on `t1` before either is done, and the whole
run takes one second instead of two:

```
open:  2026-10-13T21:29:59+02:00
start alice v bob on t1
start carol v dave on t1
done  alice v bob
done  carol v dave
close: 2026-10-13T21:30:00+02:00
games: alice 1, bob 1, carol 1, dave 1
tables: t1 2, t2 0
```

The generated `Play()` shows why. The closure passed to `ScheduleMulti` (the runtime call that
acquires a set of cowns atomically, in [`cown.go`](../../../compiler/runtime/rt/cown.go)) ends
right after the child call is started. Everything after it runs later, outside the closure:

```go
_sched := std.ScheduleMulti([]*std.Cown{&self.Cown, &self.a.Cown, &self.b.Cown, &self.t.Cown}, func() std.Unit {
    std.Print(/* start ... */)
    _st0 := std.Time.Sleep(std.NewInt(1))
    _bg0.Add(func() { _st0.Await() })
    return std.TheUnit
})                                  // all four cowns released here
return std.LazyUnit(std.NewThunk(func() std.Unit {
    _sched.Force()
    _bg0.Wait()                     // the child finishes here, nothing held
    self.a.played = self.a.played.Plus(std.NewInt(1))
    self.b.played = self.b.played.Plus(std.NewInt(1))
    self.t.games = self.t.games.Plus(std.NewInt(1))
    return std.Print(/* done ... */)
}))
```

It is not specific to `time.sleep`. Replacing that one line gives the same split each time:

| Child call inside `play` | Child | Generated shape |
|---|---|---|
| `time.sleep(1)` | runtime builtin, owns no cown | split after the call |
| `pause()` | `pause: { print("pausing") }`, a user boc that needs nothing `play` holds | split after the call |
| `n: tally(t)`, with `n` used afterwards | `tally #(t Table, Int) { t.games }`, a user boc that needs the held table | split after the call; `tally` itself is a plain `ScheduleMulti` on `{tally, t}` |

The runtime's queueing is not at fault. With the generated Go edited by hand so the sleep is
awaited and the remaining statements run inside the `ScheduleMulti` closure, the same program runs
the two matches one after the other in about two seconds, and moving the second match to `t2`
brings it back to one.

## Consequences

1. **A resource is not held across a child call.** The user-facing model says only one running boc
   holds a resource at a time. From the outside, `play` gives up the table at its first child call.
2. **The rest of the body is unprotected.** The writes to `a.played`, `b.played` and `t.games` run
   with no cown held. In the plain-boc form of the same demo (`boil #(dish String, s Station)`,
   called twice) the second call overwrote the singleton's `dish` field before the first call's
   remaining statements read it, and `done soup` printed twice.
3. **`Concurrency.md` documents behaviour the compiler does not provide.** Its producer-consumer
   diagram draws `time.delay(1)` inside the section marked "holding resource for this iteration".

## What is already decided, and what it does not cover

- **Release before waiting.** [`concurrency-design.md`](../concurrency-design.md), "Re-entrancy":
  a parent that waits for a child while holding the cown the child needs deadlocks, so
  `BocGroup.Wait()` moves after the release. The example there has no statements after the child
  call.
- **Where a child goes in the queue (YZC-0036).** The
  [solved while-loop question](../../Questions/solved/While%20loop%20yield%20and%20external%20caller%20interleaving.md):
  a non-recursive inner call runs next in line through `ScheduleAsSuccessor`, and a recursive call
  goes to the tail so `while` yields between iterations. In `emitImmediateBody`
  ([`codegen.go`](../../../compiler/internal/codegen/codegen.go)) the successor path is taken only
  for a method call whose receiver's cown is held. A boc that receives the held resource as an
  argument, like `tally(t)` above, does not take it.
- **Synchronous rewrite (YZC-0008).** A leaf callee whose cown is already held runs as a plain
  call.
- **`ScheduleFlatten`.** When a same-cown child is forced inline, the continuation reacquires the
  cowns through a nested `ScheduleMulti`.

Each of these is about the child: whether it deadlocks, and where it queues. None says where the
parent's remaining statements run, or what they hold, after a child call in statement position.

## Not confirmed

- The lowerer code that performs the split was not read. Everything above comes from generated Go
  and the design documents.
- That `tally(t)` queues behind the second match already waiting on `t1`. It is inferred from the
  call being emitted as `ScheduleMulti` rather than `ScheduleAsSuccessor`, not from a trace.
- Whether another caller can run between a `ScheduleFlatten` body's first part and its reacquired
  continuation.
- The race in the instance form was not observed as a wrong number: the counts came out right in
  every run of the repro.

## Open decision

After a boc calls a child:

1. Does the parent keep its resources until its own body ends?
2. Where do the parent's remaining statements run, and holding what?

Whatever the answer, three things that work today have to keep working:

- A child that needs the parent's own resource does not deadlock.
- `while` lets outside callers in between iterations (YZC-0036).
- In `foo → bar → baz`, `baz` runs next in line and not behind outside callers.

## Proposal (current thinking, not decided)

Treat a whole body as one turn, and extend the YZC-0036 rule to the parent's continuation:

- **Child that needs no resource at all, or a leaf that needs none the parent holds:** the parent
  keeps its resources and waits for the child inside the acquisition. This case alone makes the
  repro behave.
- **Non-recursive child that needs a held resource:** the child runs next in line, then the
  parent's remaining statements run next in line after it with the resources reacquired. This
  should hold when the resource is passed as an argument, not only when it is the receiver.
- **Recursive call:** the turn ends and the call goes to the tail, as today.

One case has no answer yet: **a non-leaf child that needs other resources.** Keeping the parent's
resources while waiting for it reintroduces deadlock. `P` holds `A` and waits for a child that
needs `B`, while `Q` holds `B` and waits for a child that needs `A`. Releasing first, as today, is
safe but leaves the remaining statements unprotected. Reacquiring for the remaining statements
protects them but lets another caller in between, so the body is no longer atomic.
