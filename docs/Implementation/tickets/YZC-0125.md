# Sibling boc calls run sequentially

`YZC-0125`

**A boc call is not queued when it is made, only when its caller waits for it, so
sibling calls run one after the other.** This happens whenever the callee's body itself calls a
boc in statement position, which is most real bodies (`print` is enough to make the timing hard to
see; `time.sleep` makes it obvious).

## Observed

```yz
main: {
    a()
    b()
}

a: {
    print("a start")
    time.sleep(1)
    print("a done")
}

b: {
    print("b start")
    time.sleep(1)
    print("b done")
}
```

Output with `yzc v0.5.0-e08b58a`. `b` does not start until `a` is done, and the run takes two
seconds instead of one:

```
a start
a done
b start
b done
```

Found in a ping-pong program where `main` calls `ping(10, 1, "ping")` and `pong(5, 2, "pong")`:
all ten `ping` lines printed before the first `pong`. Giving each its own loop boc did not help,
because neither call was queued until `main` waited for it.

## Cause

The generated `A.Call()`:

```go
return std.LazyUnit(std.NewThunk(func() std.Unit {   // cold: nothing below runs yet
    _bg0 := &std.BocGroup{}
    std.Schedule(&self.Cown, func() std.Unit {        // a joins its queue only when forced
        std.Print(std.NewString("a start"))
        _st0 := std.Time.Sleep(std.NewInt(1))
        _bg0.Add(func() { _st0.Await() })
        return std.TheUnit
    }).Force()
    _bg0.Wait()
    std.Print(std.NewString("a done"))
    return std.TheUnit
}))
```

`NewThunk` ([`thunk.go`](../../../compiler/runtime/rt/thunk.go)) does not run its function until
the first `Force()`. `main` adds `a()` and `b()` to its `BocGroup`, and `BocGroup.Wait`
([`core.go`](../../../compiler/runtime/rt/core.go)) forces them in order. So `a` is queued, runs,
and finishes its own `Wait()` before `b` is queued at all. `BocGroup`'s own comment states the
assumption this breaks: "Underlying goroutines are already running (started by Schedule inside the
cown), so sequential forcing loses no parallelism."

The shape comes from the single-cown split-BocGroup branch of `emitThunk`
([`codegen.go`](../../../compiler/internal/codegen/codegen.go)), which has emitted it since Phase A
(`7e0e130`). Its multi-cown counterpart, `emitScheduleMultiSplit`, started with the same shape in
Phase E.1 (`fb294e0`) and was made eager the same day in `aeccc35`, "so that cown queue positions
are established immediately when Call() is invoked, preserving BOC spawn-order determinism". The
single-cown branch was not changed with it.

Bodies with no statement-position boc call take the plain `std.Schedule(...)` branch, which is
already eager. Instance methods go through the same branch: `Worker: { name String; run: { ... } }`
with the same body, called as `a.run(); b.run()` on two instances, also prints `a done` before
`b start` and takes two seconds.

## Confirmed

With the generated Go edited by hand to the `emitScheduleMultiSplit` shape (`_sched :=
std.Schedule(...)` outside, `NewThunk` around `_sched.Force(); _bg0.Wait()` only), the ping-pong
program interleaves its output (`pong ping ping pong ...`). The recursive `while` placeholder in
that program still yields between iterations after the edit.

## Fix

Make the single-cown split branch of `emitThunk` match `emitScheduleMultiSplit`: an IIFE that calls
`std.Schedule` straight away, then returns a `NewThunk` that forces it and waits for the
`BocGroup`.

- Add a golden test with the repro above. No golden test calls `time.sleep` today, and its output
  has to show `a start` and `b start` before either `done` line.
- 48 golden `.go` files contain the cold shape, so expect a large but mechanical golden diff.
- Check that `while` still yields to outside callers between iterations (YZC-0036). Today the
  yield happens partly because the recursive call is cold and is queued only after the cown is
  released. Once eager, it is queued while the cown is still held, at the tail, behind any caller
  already waiting. Goldens `05_while`, `38_recursive_boc` and `39_local_boc_recursive` should
  cover it.
