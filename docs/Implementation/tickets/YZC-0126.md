# Constructor call at the start of a statement fails to parse in a type's methods

`YZC-0126`

**In a `name: { ... }` method of an uppercase boc, a statement that starts with a constructor call
is parsed as a variant declaration.** The decided `while` dispatcher form
([`stdlib.md`](../../Questions/stdlib.md)) hits this at `While(cond, body).run()`.

## Observed

```yz
Box: {
    n Int
    m Int
    show: { print("box ${n} ${m}") }
    copy: { Box(m, n).show() }
}
main: { Box(3, 4).copy() }
```

With `yzc v0.5.0-e08b58a`:

```
error: expected type expression, got COMMA(",")
 --> main.yz:5:18
```

With literal arguments, `copy: { Box(1, 2).show() }`, the error is `expected boc parameter, got
INT_LIT("1")`. The same happens inside a `?` arm in the method, and when the call is in another
type's method (`Maker: { ... make: { Box(m, n).show() } }`).

These parse:

- The same call in a lowercase boc: `main: { Box(m, n).show() }`.
- The call not at the start of the statement: `copy: { b: Box(m, n); b.show() }`.
- The signature form of the method: `copy #() { Box(n).show() }`.

## Cause

`parseBocElement` ([`parser.go`](../../../compiler/internal/parser/parser.go)) parses
`TYPE_IDENT '('` as a variant declaration while `inTypeBoc` is true. Its comment states the
intent: "In value bocs (function/method bodies), TYPE_IDENT '(' is a constructor call". The flag is
set for the value of an uppercase `Name: { ... }` declaration, and reset to false only in the
`BocDecl` path (`name #(...) { }`). A `name: { ... }` method inside the type is a short declaration
whose value is a boc literal. Nothing resets the flag for it, so its body, and every boc literal
nested in it, is parsed as if it were the type's direct body.

## Fix

Reset `inTypeBoc` to false when parsing the value of a lowercase `name: { ... }` declaration, as the
`BocDecl` path already does. Add a parser test for each of the three failing forms above.
